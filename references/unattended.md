# Daily unattended runs (PC off)

Set it up once; every day at your chosen time the same routine runs on your phones and you get a report.

```
Google Sheet (you edit with dropdowns)                       Runner (VPS or GitHub Actions, PC not needed)
  Phones / Library / Routine / Settings                         checks the queue every few minutes
        |  daily at run_time: Apps Script copies                       |  starts each cloud phone that has tasks
        v  the Routine into the Tasks queue                            v  runs its tasks IN ORDER, one after another
  Tasks (queue) <---- claim / report --------------------------> bulk-run --only-cloud
  Reports / Runs / Overview (update live)                              |  stops every phone it started
  Email report when the day finishes                                    v  done; next check is a free no-op
```

The cloud phones, their ADB and the sheet all live in the cloud. Only the small runner program needs a machine that is always on.

## 1. The sheet (everything is a dropdown)

Run `setup()` once from Apps Script (see [bulk_automation.md](bulk_automation.md)). It creates:

| Tab | You | What it is |
| :--- | :--- | :--- |
| **Phones** | fill once | One row per phone: tick `enabled`, a `label` you choose ("Phone 4"), `type` (dropdown: cloud / local), `phone_id` (GeeLark profile id), and optionally a `group` (for example "Warmup"). |
| **Library** | rarely touch | The tasks you can pick: "Open YouTube", "Watch YouTube video", "Skip ad if shown", "Take screenshot", ... Each is an action plus a parameter template. Add your own by picking an action from the dropdown. |
| **Playbooks** | the reusable routines | A named list of steps, one row per step, in order: pick the `task` from the Library and, if it needs one, a `value` and `duration_s`. Write the playbook name on its first row only. Leave a step's value or duration blank to let the Routine row that uses the playbook supply it. Playbooks can't contain playbooks. |
| **Routine** | the daily plan | One row per step: tick `enabled`, **pick the phone, or type a group name** (every enabled phone in that group gets the step), **pick the task, or a playbook** (dropdown from Library and Playbooks; a playbook runs all its steps in order for each phone), then only if the task needs it a `value` (a link or text) and a `duration_s` (dropdown). **Row order is run order**, per phone. |
| **Settings** | once | `run_time` (dropdown, every 15 min), `enabled`, `paused` (emergency stop), `on_failure`, retries, limits, `report_email`. |
| **Tasks** | read only | The queue. Each morning's rows are created for you; colours show pending / running / success / failed. |
| **Reports**, **Runs** | read only | One row per task result plus events (retries, offline, warnings); one summary row per runner pass. |
| **Overview** | read only | Status, next run, today's counts per phone with progress bars, last runner pass. It is built from formulas over Tasks and Runs plus a hidden `_state` tab the script keeps current. |

Typical routine for a phone: `Open YouTube` > `Watch YouTube video` (value = link, duration = 120) > `Take screenshot` > `Press Home`.

With playbooks the whole daily plan can be two rows: `Watch` (a group) + `Watch routine` (a playbook), and `Browse` + `Browse routine`. Change a playbook once and every phone in every group that uses it follows. If a name is both a Library task and a playbook, the Library task wins.
A phone takes its next task only when the previous one has finished. Different phones run at the same time (up to `max_cloud_phones`).

**Look and chips.** The design (header colours, fonts, column widths, banded rows, status colours, the Overview layout, and dropdown *chips*) is applied to the sheet itself, not generated by the script. Apps Script's own `DataValidationBuilder` cannot create chips ([docs](https://developers.google.com/apps-script/reference/spreadsheet/data-validation-builder)), but the Sheets API can (`customUiMode: "CHIP"`), which is how the pickers in the reference sheet were made. `setup()` never overwrites an existing dropdown, colour rule, width or the Overview tab, so re-running it is safe. A brand-new sheet gets plain arrow dropdowns and no styling until the design is applied through the Sheets API (or by hand under Data > Data validation, which has a chip display style).

**Daily schedule.** A trigger checks every 5 minutes whether it is past `run_time` and the day has not been queued yet. Missed by more than 6 hours (e.g. Google outage) = skipped with a warning rather than running at night. Changing `run_time` takes effect on the next check. The first run after `setup()` is the next occurrence of `run_time`, never "right now". Use **GeeLark > Run the routine now** for a manual batch, and **Preview** to see what would be queued without queuing it.

**Failures.** `on_failure = continue` keeps going after a failed task; `stop` marks that phone's remaining tasks `skipped` (other phones are unaffected). Unfinished tasks from a previous day are marked `expired`, never run late.

**Email.** Set `report_email` to get one email when every task of the day has finished (or an "INCOMPLETE" email if the runner has not finished `max_runtime_min` + 30 minutes after the queue was created). The first `setup()` asks you to approve sending mail.

## 2. Choose where the runner lives

Both options run the same command, `python scripts/geelark.py bulk-run --only-cloud --waves 3`, which:
* exits silently (writes nothing) when nothing is waiting, so frequent checks are free;
* reads limits from the Settings tab (a flag on the command line overrides it);
* never takes tasks without a `cloud:` device, never runs two copies at once on one machine;
* starts at most `max_cloud_phones` phones at a time and, with `--waves N`, starts the next batch when one finishes (20 phones at 10 a time needs `--waves 2` or more);
* enforces two spend caps from Settings: `max_phone_minutes` (a phone takes no new task after that long) and `daily_phone_minutes` (no new phone or task once the day's total is reached; the total is kept across runs in `logs/.phone_minutes.json`);
* spaces its GeeLark API calls (default 150 a minute, override with `GEELARK_API_RATE_PER_MIN`; the API's limit is 200).

### Option A: Linux VPS (recommended: precise timing, simplest to reason about)
Any small Debian/Ubuntu server.
```bash
git clone https://github.com/toruu7/geelark-cloud-phone && cd geelark-cloud-phone/deploy/vps
sudo bash install.sh            # installs adb + python, a locked-down service user, the units
sudo nano /etc/geelark.env      # token, sheet URL, sheet secret (mode 600)
sudo systemctl start geelark-bulk.service && journalctl -u geelark-bulk.service -n 50 --no-pager   # one manual pass
sudo systemctl enable --now geelark-bulk.timer                                                      # then every 5 minutes
```
`install.sh` fetches the `geelark-cloud-adb` skill from `ADB_REPO` (default `https://github.com/toruu7/geelark-cloud-adb`). That repository must exist and be readable by the server: create it on GitHub and push your local copy first (or point `ADB_REPO` at wherever it lives).
Billing safety in the unit: SIGTERM is turned into "stop every phone we started" (`KillMode=mixed`, 5-minute grace), `RuntimeMaxSec=3h` is a hard cap, and `ExecStopPost` stops any phone still registered even after a crash.

### Option B: GitHub Actions (no server)
Copy [deploy/github/geelark-bulk.yml](../deploy/github/geelark-bulk.yml) to `.github/workflows/` in a **private** repository containing this project, add the secrets listed at the top of the file, and set the cron window (UTC) to start at your `run_time`.
* A cheap first step asks the sheet whether anything is waiting (`--probe`); ADB is only installed and phones only started when there is work.
* `concurrency` prevents overlapping runs; a final `always()` step stops any phone left running, even after a cancel or timeout.
* Limits to know: scheduled runs can start late or be skipped under GitHub load, the minimum interval is 5 minutes, scheduled workflows are paused after 60 days without repository activity, and private repositories have a monthly minutes allowance. The narrow cron window keeps usage low.

### Option C: a Claude cloud routine (no server, no GitHub Actions)
Claude's scheduled tasks can run the daily pass in Anthropic's cloud, so the PC can be off. A *cloud* task (not "Only on this computer") clones this repository, and Claude Code loads the skills in its `.claude/skills/` folder:
* `geelark-daily-operator`: the playbook the unattended agent follows (probe, run once, stop every phone, report, hard safety rules).
* `geelark-cloud-adb`: your phone-control skill (a vendored copy, so one clone is self-contained). The runner also uses its script to start and stop the cloud phone.

Setup:
1. **Connect GitHub** to your Claude account (https://claude.ai/connect-github) so the routine can clone the repository.
2. **Add three environment variables** to the cloud environment's settings: `GEELARK_API_TOKEN`, `GEELARK_SHEETS_URL`, `GEELARK_SHEETS_SECRET`. Never put them in the prompt. Also set `GEELARK_TRANSPORT=api`: the Claude cloud sandbox only allows web traffic through a proxy, so ADB over TCP cannot work there. In API mode the runner uses GeeLark's HTTPS API only (`shell/execute` for taps, text, app launch and UI reads; `phone/screenShot` for screenshots), so no adb is needed (Android 10+ cloud phones). Set the environment's network access to Custom and allow `openapi.geelark.com`, `script.google.com` and `script.googleusercontent.com`; screenshots are downloaded from a GeeLark storage host that is also needed (the screenshot task's output records it as `download_host`), or use Full network access.
3. **Create the routine**: repository `toruu7/geelark-cloud-phone`, prompt = [`deploy/claude-routine/prompt.txt`](../deploy/claude-routine/prompt.txt), tools Bash and Read (plus Skill if offered), no connectors, a daily schedule shortly after `run_time`. Cron is in UTC with a one-hour minimum interval: `run_time` 09:00 in Asia/Dhaka (UTC+6) means the sheet queues at 03:00 UTC, so schedule `15 3 * * *` (09:15 Dhaka).
4. Keep the vendored skill current with `python scripts/sync_cloud_adb.py` (pulls the pinned latest commit of the upstream repo; review and commit).

How it differs from the other options: the agent does not decide what the phones do (the sheet's plan does, through the same runner); it supervises. Each run is one Claude session, so it uses some of your Claude usage, and a scheduled run can start a few minutes late. A run that dies mid-way can leave a phone running; the next run cannot see it because each cloud sandbox is discarded, so rely on `max_runtime_min`, the task timeouts and the runner's own stop-on-exit handling, and check the Overview after the first runs.

## 3. Safety and cost

| Risk | Protection |
| :--- | :--- |
| Forgotten billing | Every phone the runner starts is stopped when its tasks end, on failure, on SIGTERM/Ctrl+C, in a final sweep that retries, and by an extra cleanup step in both deployments. `STOP FAILED` is reported loudly (Reports, Runs notes, email). A killed process leaves `logs/.cloud_active.json`; the next pass warns and `bulk-cloud-stop` stops those phones. |
| Runaway runs | `max_runtime_min` (no new tasks after it), `task_timeout_s`, `retries`, `max_cloud_phones`, a 3 h hard cap on the VPS, 120 min on Actions. Each task runs at most once per day (plus in-run retries): failed tasks are not re-queued. |
| Surprises | `paused` in Settings stops the runner and the daily queue instantly (no redeploy). `enabled` off = no daily batch. Old batches expire. |
| Overlap | One run per machine (file lock), `concurrency` on Actions. Run only one runner for the same phones. |
| Secrets | Token and sheet secret live in `/etc/geelark.env` (600) or GitHub Secrets, never in the repo or the sheet. Use a fresh API token for the server and rotate any token that was ever pasted into chat. |
| Bad rows | Routine mistakes (unknown phone/task, missing link) become `error` rows in Reports and are listed in the email; they never stop other rows. |

Cost to expect: phone-minutes while a phone is up (boot takes about a minute, plus the tasks). The `Runs` notes show roughly how many phone-minutes each pass used. Start with a short routine on one phone and watch the first few days.

## 4. First-day checklist
1. Fill **Phones** (tick `enabled`) and a 2-3 step **Routine**; use **GeeLark > Preview** and fix any problems it lists.
2. Set `run_time` a few minutes ahead, `report_email`, and leave `max_cloud_phones` at 1 or 2.
3. Start the runner once by hand and watch one pass finish; confirm in GeeLark that the phone stopped.
4. Enable the timer (VPS) or the workflow (Actions). Tomorrow check the Overview, Reports and your email.

## Troubleshooting
| Symptom | Check |
| :--- | :--- |
| Nothing was queued at run_time | Settings: `enabled` ticked, `paused` not ticked, time zone right; the 5-minute trigger exists (setup installs it); Reports has a `schedule` row for the day. |
| Tasks queued but nothing runs | Runner not scheduled / secrets missing; `bulk-run --only-cloud --probe` should print `work`. Tasks need a `cloud:` device: set Phones `type` to cloud and a profile id. |
| `error` rows from "Routine row N" | The message says what to fix (phone not in Phones, task not in Library, missing value or duration). |
| Phone started but tasks failed | Reports `message`/`output`; `assert-text` and `open-app` explain what was on screen. Add a `Skip ad if shown` or `Press Back` step where a dialog gets in the way. |
| A screenshot shows a wall ("not a bot", "Video unavailable", Chrome's first-run page...) | The `Take screenshot` task now reads the screen and **fails** with `blocker: <kind>` when it finds a known blocker phrase; the screenshot is still saved and the message shows the text. A screen that cannot be read (a playing video) is never reported as a blocker, so a clean result is not proof that nothing is wrong: still glance at the screenshots. Never click through a bot check from automation; fix the phone, proxy or login by hand. Turn the check off for one step with `"blockers": false`. |
| No email | `report_email` set; `setup()` re-run to approve mail permission; Gmail daily send quota; check the Reports `email` rows. |
